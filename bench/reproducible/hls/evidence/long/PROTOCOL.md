# Linux DEV HLS proxy comparison — 60-second measurement

Each of 11,776 simulated viewers requests one 3,000,000-byte segment every six seconds, for 4 Mbps/viewer and 47.104 Gbps of offered loopback payload. At each arm, a fresh proxy and RAM origin bind ephemeral IPv4 loopback sockets. HTTP/1.1 with downstream connection reuse, proxy vCPUs 12–13 (Go GOMAXPROCS=2 or two Actix workers), origin 8–11, driver 4–7, coordinator 2. Services, runners, kernel and GC settings remain as found. The exact archived builds from the short comparison are used. See harness/SHA256SUMS and BUILD.md.

Each of five blocks has all three arms. The fixed order is WFA, FAW, AWF, AFW, FWA, where W is Wing 256 KiB + StreamKeepAlive, F is Fiber, A is Actix Web + Reqwest. Each arm schedules exactly 11,776 warm requests (6 s) and 117,760 measured requests (60 s). No extra scored arm, fallback rate or selective rerun. Payload ceilings are for this scheduled workload. The same client schedules all three arms with one 512-request in-flight cap and shared HTTP transport. A request belongs to the phase of its scheduled time, including when it completes across the phase boundary. No drain or connection reset between phases. A skipped dispatch at the cap and any unsuccessful dispatched request are separately counted in each phase.

Use the archived origin binary. Recover the common load driver's source and patch from the Tiinno benchmark history. Preserve request schedule, connection policy, parallelism, timeout, response checks and the scored 1,001 ms minimum guard-miss penalty. This phase-instrumented driver uses one result slot per scheduled request in both phases, applies the same checks, and reduces after all requests stop. Extra warm-phase stores/allocation mean it is a new driver build. The three scored stacks share the exact same driver executable.

Preflight exact 200/206 response content SHA-256, HEAD metadata and GET/Range/GET same-socket reuse across 6.05 s. Confirm runner and phase accounting at small scale before scoring. Expected gate thresholds are <=20 ms measured dispatch p99, <=1 s measured scheduled-to-full-response p99, 99% measured downstream reuse, every scored response correct status/full length/unique origin ID, and zero measured misses. Full pass additionally requires every warm response complete and unique, cross-phase uniqueness and origin hits matching warm+measured totals. Failed p99 values include penalty, while equal-delivery latency/CPU comparisons use joint full passes. No stale JSON, cherry-picked outcomes or output-only control. CPU is the proxy process's user+system ticks sampled around the 60 s measured interval; 100% equals one vCPU. RSS median and peak are sampled around every 0.2 s. Keep host and client/origin resource controls.

Claim under test: at this single virtualized Linux DEV host and configured loopback load, compare delivery consistency over five 60-second windows, including the missed warm and steady work. Any finding applies to the actual tested builds and driver, not production listener capacity.

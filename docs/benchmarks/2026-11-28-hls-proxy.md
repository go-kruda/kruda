# HLS segment proxy benchmark

Kruda v1.9.0 can reuse a Wing HTTP/1.1 connection for fixed-length HLS segment downloads and byte-range reads. Use the released example to check that behavior on Linux. The separate 256 KiB experiment compares three proxy configurations on Linux loopback.

[Try v1.9.0](#released-kruda-v1-9-0) · [Read the experimental results](#experimental-wing-256-kib) · [Download source and raw evidence](/benchmark-data/2026-11-28-hls/kruda-hls-reproduction.zip)

## Released Kruda v1.9.0

The released option reuses the connection after a streamed GET 200 or 206 when the response declares an exact positive `Content-Length` and `c.Stream` writes that many bytes.

```go
app.Get("/media/:name", streamSegment,
    kruda.Stream.With(kruda.StreamKeepAlive()))
```

In the release qualification, Wing and net/http each completed all five 60-second rounds at **5,120 simulated viewers**. Each proxy had one vCPU. The Go load driver scheduled one 3,000,000-byte segment every six seconds per viewer on Linux HTTP/1.1 loopback.

| v1.9.0 transport | Passing rounds | Segment p99 median and range |
| --- | ---: | ---: |
| Wing | 5/5 | 8.0 ms, 6.3 to 8.9 ms |
| net/http | 5/5 | 6.2 ms, 5.0 to 7.5 ms |

Both transports had zero failed requests and complete origin-hit counts in this qualification. [Read the release notes](https://github.com/go-kruda/kruda/releases/tag/v1.9.0#hls-and-byte-range-streaming-on-wing-streamkeepalive).

### Run the released example

Extract the download on Linux. With Go and Python 3 installed, run:

```sh
bash build.sh release
bash run.sh release
```

The example starts a loopback RAM origin and a Wing proxy using the published v1.9.0 module. The check verifies the full GET body, Range bytes, HEAD metadata, and TCP connection reuse after a six-second interval.

## Experimental Wing 256 KiB

::: warning Experimental build
These results use a v1.9.0-based Wing build with a pooled 256 KiB copy buffer and `StreamKeepAlive`. The pooled-buffer patch is separate from the v1.9.0 release.
:::

Both profiles used two pinned vCPUs per proxy, a RAM origin, and HTTP/1.1 over Linux TCP loopback. The driver scheduled one 3,000,000-byte segment every six seconds per simulated viewer, equivalent to 4 Mbps per viewer. All stacks shared a client cap of 512 in-flight requests.

### Delivery at 11,776 simulated viewers

The experimental Wing build completed all **588,800 scheduled segments across five 60-second measurement windows**. It missed 69 of 58,880 scheduled segments during one warm-up. It passed all five measurement windows and four of five full rounds.

<BenchBars :groups="delivery" unit="%" direction="Five 60-second measurement windows" />

| Proxy build | Completed in measurement | Unsent in measurement | Unsent during warm-up |
| --- | ---: | ---: | ---: |
| Wing 256 KiB | 588,800 / 588,800 | 0 | 69 |
| Fiber v3.7.0 | 525,322 / 588,800 | 63,478 | 4,912 |
| Actix Web v4.20.0 + Reqwest v0.12.28 | 377,512 / 588,800 | 211,288 | 17,953 |

The driver skipped each unsent request when it hit the in-flight cap. All dispatched requests returned HTTP 200 with the expected byte count. At this load the stacks had no jointly passing rounds for an equal-delivery p99 comparison.

The schedule offered **47.104 Gbps of media payload on loopback**. Production viewer capacity depends on the network, proxy deployment, origin, and player behavior.

### Equal work at 6,144 simulated viewers

Each stack completed all **61,440** measured segments and passed all five 12-second rounds. Segment p99 measures time from scheduled dispatch to the full response body. CPU 100% represents one vCPU. RSS is process resident memory sampled about every 200 ms.

<BenchBars :groups="latency" unit="ms" direction="Lower is better at equal delivered load" />

| Proxy build | Segment p99 median | Proxy CPU median | RSS median / sampled peak |
| --- | ---: | ---: | ---: |
| Wing 256 KiB | 3.42 ms | 90.86% | 20.66 / 21.76 MiB |
| Fiber v3.7.0 | 3.96 ms | 108.16% | 14.48 / 15.08 MiB |
| Actix Web v4.20.0 + Reqwest v0.12.28 | 3.44 ms | 90.45% | 10.40 / 12.29 MiB |

Wing used less CPU and had lower p99 than Fiber in all five paired rounds, with higher RSS. Wing and Actix had similar CPU and p99 at this load. Actix used less RSS.

### Reproduce or inspect the measurements

[Download the reproduction package](/benchmark-data/2026-11-28-hls/kruda-hls-reproduction.zip). Its README provides build and run commands, toolchain versions, CPU placement, and measurement gates. The package contains the Wing patch, the Fiber and Actix source and lockfiles, both load drivers, and the original result rows and process samples. Run the 64-viewer smoke check before the 6,144- or 11,776-viewer workloads.

The two reports retain per-round variation, the complete warm-up and measurement accounting available for each driver, and the checks for status, byte counts, and origin hits. Use the replay scripts to check the reports against the archived data.
